# 03 — Message Model, Synchronization, Local Database

## 1. Identifiers

| ID | Generated by | Purpose |
|----|--------------|---------|
| `message.id` | client, UUID (lowercase) | Stable application-level ID; the UI and all local references use this |
| `originId` | client = `message.id` for own messages; for foreign messages, the sender's `<origin-id>` | Sent as stanza `id` **and** XEP-0359 `<origin-id>`; target of corrections, retractions, receipts, markers, replies in 1:1 |
| `stanzaId` | server (XEP-0359 `<stanza-id by=archive>`) | Unique per archive (own account or room); MAM paging cursor; reaction/reply target in groups |
| `conversation.id` | client, UUID | Local primary key; the peer/room JID is a unique secondary key |

Users never see any of these.

## 2. Message model

Kinds: `text`, `image`, `video`, `file`, `voice`, `system` (member joined, device changed,
undecryptable, …).

Supported operations and wire mapping (all content elements are inside the OMEMO SCE envelope):

| Feature | Spec | Notes |
|---------|------|-------|
| Reply | XEP-0461 | Quoted preview built locally from the referenced message; a fallback quote is included for robustness |
| Edit | XEP-0308 | Only own messages, no time limit in MVP; UI shows "edited" |
| Delete for me | local | Row tombstoned locally |
| Delete for everyone | XEP-0424 | Best effort: compliant clients (ours) remove it; documented as such in the UI |
| Reaction | XEP-0444 | Full reaction set per reactor (replace semantics) |
| Forward | new message | Re-sends the content; attachments reuse the encrypted blob URL + key (no re-upload) |
| Copy | local | |
| Delivery receipt | XEP-0184 | 1:1 only (unencrypted element, references `originId`) |
| Read marker | XEP-0333 `displayed` | 1:1: per message. Groups: Phase 10 ("read by N") |
| Typing | XEP-0085 | `composing`/`paused`, never stored, never archived (`<no-store/>`) |

### 2.1 Message state machine (outgoing)

```
           enqueue             SM ack / MUC reflection      receipt(any recipient device)     displayed
 (draft) ─────────► sending ─────────────────────────► sent ───────────────────────► delivered ──────────► read
                       │  permanent error / no trusted devices / 24 h unsent
                       └──────────────────────────────► failed ──(user taps Retry)──► sending
```

- States only move forward (`read` never regresses to `delivered`, even if events arrive out of order).
- "Sent" means the server has accepted the stanza (XEP-0198 ack). If the stream is resumed, unacked
  stanzas are re-sent by SM. If the stream cannot be resumed, the outbox re-sends with the **same**
  `originId`, and the receiver deduplicates.

## 3. Synchronization model

### 3.1 Sources of incoming data

1. Live stanzas on the current stream.
2. Carbons (XEP-0280): copies of own messages sent/received by other own devices.
3. MAM (XEP-0313) catch-up: own account archive (1:1 + MUC/Sub-delivered group messages) and each room archive.
4. XEP-0198 resumption: replays unacked stanzas after a short disconnect (no gap, no MAM needed).
5. PEP notifications: device lists, avatars, nicknames.

All five go through the **same ingest pipeline** in `SyncEngine`, so dedup and ordering rules are
identical everywhere.

### 3.2 Ingest pipeline (per stanza)

1. Normalize → `IncomingEnvelope { archiveJid, stanzaId?, originId?, from, to, serverTime?, payload }`.
2. **Dedup before decrypt** (an OMEMO message key can be used only once):
   - match on `(archiveJid, stanzaId)` → already have it: merge, stop;
   - else match on `(conversationId, senderJid, originId)` → merge (`stanzaId` filled in, outgoing
     status advanced if it is our own reflection/carbon), stop.
3. Decrypt via `EncryptionService` (serialized per sender device).
4. Apply in **one write transaction**: insert message / apply edit / retraction / reaction, update
   conversation summary + unread count + FTS, commit the new ratchet state, advance the sync cursor if the
   stanza came from MAM.
5. If the transaction fails, the in-memory ratchet state is discarded, so nothing advances half-way.
6. If decryption fails (no session, key already used), the row is stored as `system/undecryptable` with the
   raw stanza kept for 7 days. If a key exchange arrives later, that message is retried once.

Edits/reactions/retractions that reference a message not yet stored (out-of-order MAM) are
kept in `pending_reference` and applied when the target arrives (TTL 30 days).

### 3.3 Ordering

- `sortKey` = server timestamp (MAM `<delay>` or `<stanza-id>` arrival time recorded by the server;
  live messages use the server-stamped delay when present, else the local receive time),
  tie-broken by a monotonically increasing local sequence.
- Own outgoing messages use the local send time and keep it (no visible reordering after ack).
- The UI orders by `(sortKey, seq)`, never by arrival order. This makes out-of-order delivery harmless.

### 3.4 Catch-up procedure

```
on connect:
  if SM resume succeeded            → done (server replays unacked stanzas)
  else:
    enable carbons, send initial presence, join rooms (MUC/Sub subscription persists anyway)
    for archive in [own account] + rooms with activity:
       cursor = sync_state.lastStanzaId(archive)
       if cursor == nil: fetch the last page only (newest 50 per conversation, before=""), mark backfill incomplete
       else: page forward  <set><after>cursor</after><max>100</max></set>  until <fin complete='true'>
       each page: ingest all → commit → update cursor (crash-safe: resume from the last committed page)
older history: fetched lazily when the user scrolls up (RSM <before> oldestStanzaId), per conversation
```

- Live messages that arrive during catch-up go through the same dedup, so overlap is harmless.
- A cursor that is no longer in the archive (`item-not-found`, e.g. retention expired) → fall back
  to the "last page" strategy and insert a system row "Some older messages are no longer available".
- Multi-device: carbons + MAM give each device the full stream. Own sent messages are decryptable on
  other own devices because OMEMO encrypts to all own devices.

### 3.5 Read state across own devices

- MVP: markers sent by one own device reach the others via carbons → unread counts update.
- Phase 10: XEP-0490 Message Displayed Synchronization (PEP) for robust cross-device read state.

### 3.6 Connection management

- `NWConnection` with TLS (direct TLS, ALPN `xmpp-client`), connect timeout 15 s.
- XEP-0198 enabled with `resume='true'`. The server holds the session (resume timeout set by
  `mod_push_keepalive`, e.g. 72 h for push-enabled clients).
- Keepalive: SM `<r/>` every 60 s in the foreground; 2 missed acks → dead connection.
- Reconnect: exponential backoff 1, 2, 4, 8, 16, 32, 60 s (max) ± 20 % jitter. The backoff resets on
  `NWPathMonitor` path change (Wi-Fi ↔ cellular) or on foreground. No reconnect attempts while
  the path is unsatisfied.
- Background: on `scenePhase == .background` the app requests a short background task, flushes the
  outbox, requests a final SM ack, then **closes the socket without closing the stream**. The server hibernates the
  session and starts sending pushes. In the background we rely on APNs, not on sockets.
- Foreground: resume the stream (instant catch-up) or full reconnect + MAM.
- Optional `BGAppRefreshTask` for opportunistic catch-up (no guarantees; not relied upon).

## 4. Attachments

Upload flow:

```
pick → (image: downscale to ≤ 2560 px, strip EXIF/GPS by re-encoding; video: export H.264/HEVC ≤ 720p/1080p)
     → key = 32 random bytes, nonce = 12 random bytes
     → AES-256-GCM(file) streamed in 1 MiB chunks to a temp file (ciphertext || tag)
     → sha256(ciphertext), sha256(plaintext)
     → XEP-0363 slot request (filename = random UUID, size = ciphertext size, content-type = application/octet-stream)
     → PUT via background URLSession (survives app suspension)
     → message with XEP-0447/0448 metadata (url, key, nonce, hashes, size, media-type, name, dimensions,
       duration, waveform, inline thumbnail) inside the OMEMO envelope
```

### 4.1 Metadata classification

Anything not listed as "outside" travels only inside the OMEMO-encrypted envelope.

| Item | Where | Classification |
|------|-------|----------------|
| File bytes, thumbnail/preview, original filename, media type, dimensions, duration, waveform, caption, key, nonce, hashes | **inside** the envelope only | sensitive |
| Upload filename | outside (slot request, URL) | non-sensitive: random UUID, no extension |
| Upload content type | outside | non-sensitive: always `application/octet-stream` |
| Ciphertext size | outside (slot request, server storage) | non-sensitive, accepted: needed for the upload quota. Padding to size buckets is a possible hardening step |
| Upload/download time, uploader account | server logs | metadata, accepted (same as message metadata) |

A unit test in `AttachmentsTests` asserts that the slot request and the HTTP PUT carry no data from the sensitive row.

### 4.2 Thumbnails, download, cache, voice

- Thumbnail: generated on the device (ImageIO), ≤ 64 px longest side, JPEG q 0.5, ≤ 3 KB, embedded
  **inside the encrypted envelope**. No thumbnail is ever uploaded separately.
- Download: auto-download policy (Settings ▸ Storage): photos and voice on any network, video/files on
  Wi-Fi only, files > 25 MB manual. The downloaded ciphertext's hash is verified, then it is decrypted to the
  protected media cache and the ciphertext is deleted.
- Cache: Settings ▸ Storage shows usage per category, "keep media: 1 week / 1 month / forever",
  and "clear cache". Evicted media can be re-downloaded until the server upload expiry (default 90 days).
- Voice: AAC-LC, mono, 32 kbps, `.m4a` (AVAudioRecorder). Waveform: 64 amplitude samples
  computed while recording, stored in metadata. Encrypted exactly like any other attachment.

## 5. Local database schema

SQLite via GRDB, WAL, App Group container, file protection
`completeUntilFirstUserAuthentication` (the NSE must be able to read contacts while the phone is locked).
Every schema change is a numbered GRDB migration with a test that migrates a fixture DB from each
previous version.

```sql
-- account (single row in MVP)
account(id INTEGER PK CHECK(id=1), jid TEXT NOT NULL, username TEXT NOT NULL, display_name TEXT,
        avatar_hash TEXT, omemo_device_id INTEGER, created_at REAL)

contact(id TEXT PK, jid TEXT UNIQUE NOT NULL, display_name TEXT NOT NULL, avatar_hash TEXT,
        avatar_path TEXT, presence INTEGER NOT NULL DEFAULT 0, updated_at REAL)

conversation(id TEXT PK, kind INTEGER NOT NULL,            -- 0 direct, 1 group
             peer_jid TEXT UNIQUE NOT NULL,                -- contact bare JID or room JID
             title TEXT, avatar_path TEXT,
             is_pinned INTEGER DEFAULT 0, pin_order INTEGER,
             muted_until REAL,                             -- NULL = not muted, +inf = forever
             draft_text TEXT, draft_reply_to TEXT,
             last_message_id TEXT, last_activity_at REAL,  -- denormalized for instant chat list
             unread_count INTEGER DEFAULT 0, last_read_message_id TEXT,
             is_hidden INTEGER DEFAULT 0,                  -- "delete local chat"
             created_at REAL)
CREATE INDEX conversation_list ON conversation(is_hidden, is_pinned DESC, last_activity_at DESC);

message(id TEXT PK, conversation_id TEXT NOT NULL REFERENCES conversation ON DELETE CASCADE,
        seq INTEGER NOT NULL,                              -- local monotonic tie-breaker
        origin_id TEXT, stanza_id TEXT, archive_jid TEXT,
        sender_jid TEXT NOT NULL, sender_device_id INTEGER,
        direction INTEGER NOT NULL,                        -- 0 in, 1 out
        kind INTEGER NOT NULL, body TEXT,
        reply_to_id TEXT, forwarded INTEGER DEFAULT 0,
        sort_key REAL NOT NULL, sent_at REAL, received_at REAL,
        edited_at REAL, retracted INTEGER DEFAULT 0, deleted_locally INTEGER DEFAULT 0,
        status INTEGER NOT NULL,                           -- sending/sent/delivered/read/failed
        source INTEGER NOT NULL,                           -- live/carbon/mam/transfer (future history transfer)
        encryption INTEGER NOT NULL,                       -- 0 none(system), 2 omemo2
        trust_at_receipt INTEGER, error_code TEXT)
CREATE UNIQUE INDEX message_archive ON message(archive_jid, stanza_id) WHERE stanza_id IS NOT NULL;
CREATE UNIQUE INDEX message_origin  ON message(conversation_id, sender_jid, origin_id) WHERE origin_id IS NOT NULL;
CREATE INDEX message_page ON message(conversation_id, sort_key DESC, seq DESC);

message_fts USING fts5(body, content='message', content_rowid='rowid', tokenize='unicode61 remove_diacritics 2')

reaction(message_id TEXT REFERENCES message ON DELETE CASCADE, reactor_jid TEXT, emojis TEXT NOT NULL,
         updated_at REAL, PRIMARY KEY(message_id, reactor_jid))

receipt(message_id TEXT REFERENCES message ON DELETE CASCADE, recipient_jid TEXT, state INTEGER, at REAL,
        PRIMARY KEY(message_id, recipient_jid))           -- groups (Phase 10); 1:1 uses message.status

attachment(id TEXT PK, message_id TEXT REFERENCES message ON DELETE CASCADE,
           media_type TEXT, file_name TEXT, byte_size INTEGER, width INTEGER, height INTEGER,
           duration_ms INTEGER, waveform BLOB, thumbnail BLOB,
           remote_url TEXT, key_enc BLOB,                  -- key+nonce, AES-GCM-wrapped with the state key
           sha256_cipher BLOB, sha256_plain BLOB,
           local_path TEXT, transfer_state INTEGER, transferred_bytes INTEGER)

outbox(id TEXT PK, message_id TEXT, conversation_id TEXT, operation INTEGER, -- send/edit/retract/react/marker/receipt
       payload BLOB, attempts INTEGER DEFAULT 0, next_attempt_at REAL, created_at REAL)
CREATE INDEX outbox_due ON outbox(next_attempt_at);

pending_reference(id INTEGER PK, conversation_id TEXT, target_ref TEXT, payload BLOB, created_at REAL)

sync_state(archive_jid TEXT PK, last_stanza_id TEXT, last_synced_at REAL,
           oldest_stanza_id TEXT, backfill_complete INTEGER DEFAULT 0)

group_member(conversation_id TEXT REFERENCES conversation ON DELETE CASCADE, jid TEXT,
             affiliation INTEGER, nick TEXT, PRIMARY KEY(conversation_id, jid))

-- OMEMO store: every private/secret column is AES-256-GCM encrypted with the Keychain state key
omemo_device(jid TEXT, device_id INTEGER, label TEXT, identity_key BLOB,  -- Ed25519 public
             trust INTEGER NOT NULL, first_seen REAL, last_message_at REAL, active INTEGER,
             PRIMARY KEY(jid, device_id))
omemo_session(jid TEXT, device_id INTEGER, state_enc BLOB NOT NULL, updated_at REAL,
              PRIMARY KEY(jid, device_id))
omemo_skipped_key(jid TEXT, device_id INTEGER, ratchet_pub BLOB, n INTEGER, key_enc BLOB, created_at REAL,
                  PRIMARY KEY(jid, device_id, ratchet_pub, n))
omemo_prekey(id INTEGER PK, public BLOB, private_enc BLOB, consumed INTEGER DEFAULT 0)
omemo_signed_prekey(id INTEGER PK, public BLOB, private_enc BLOB, signature BLOB, created_at REAL)

setting(key TEXT PK, value BLOB)                            -- non-secret settings only
```

Not in the DB: the password / FAST token, the OMEMO identity private key, the state key, and the push payload key
(all in the Keychain).

Performance rules:

- Chat list = single indexed query over `conversation` (denormalized summary). No joins over messages.
- Chat screen = keyset pagination of 50 rows on `message_page`. Never `OFFSET`, never a full history load.
- Search = FTS5 `MATCH` with prefix queries, limited to 100 hits, plus `LIKE` on contact names.
  Runs entirely on-device.
