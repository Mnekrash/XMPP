# S4 — MAM / Stream Management / reconnect / deduplication

**Verdict: PASS.** All 14 scenarios passed in 3 consecutive full runs (42/42), plus 6 unit tests.

Scope of the PASS:
- What passed is the canonical identity strategy and ingest engine (real Swift code on GRDB/SQLite) against the
  real ejabberd 26.09 behaviour (SM resume, failed resume, offline storage, MAM, carbons).
- The XMPP transport in this test is slixmpp, standing in for the library that D3 will choose. The scenarios
  are transport-agnostic and must be **re-run with the final Swift transport** (added as a D3 exit criterion).
- Wi-Fi/cellular transitions are simulated by aborting TCP connections; a real path change happens on the iPhone in S2.

**Date:** 2026-10-02 · **Code:** `spikes/s4-sync/`

## Objective

Prove effectively-once visible delivery: the same logical message appears exactly once in the local
database/UI across reconnects, SM resume and its failure, MAM catch-up, app restarts, duplicates and reordering.

## Canonical message identity (implemented in `SyncCore/SyncStore.swift`)

| Identifier | Generated by | Scope | Used for |
|------------|--------------|-------|----------|
| **Application message ID** (`app_id`) | sending client, lowercase UUID, once per logical message | global, stable across retries, devices and archives | identity of the logical message; target of replies/edits/reactions/receipts. Sent as stanza `id` **and** `<origin-id>`. Foreign messages without origin-id: `sid:<archive>/<stanza-id>` |
| **origin-id** (XEP-0359) | = `app_id` | travels end to end | dedup of **re-sent copies**: after a failed resume the client re-sends with the same origin-id, and the server stores a second copy with a **new** stanza-id |
| **stanza-id** (XEP-0359, `by` = archive) | server, per stored copy | per archive (own account or room) | dedup of the **same stored copy** arriving via live / SM replay / offline / MAM. One logical message can own several (table `message_server_id`) |
| **MAM result id** (`<result id>`) | server | per archive | RSM paging cursor only. **Measured: equal to the live `<stanza-id>` on ejabberd 26.09** (t01) |
| **Local DB primary key** (`local_id`, SQLite rowid) | local database | this device only, never sent | joins, FTS, pagination tie-break |

Ingest rule (one write transaction per stanza; **dedup before decrypt**):

1. `(archive, stanza-id)` already known → `duplicateServerId` (no decrypt, no change).
2. Else `(peer, sender, origin-id)` known → `mergedByOriginId`: record the new stanza-id; an own `sending`
   message becomes `sent` (a server copy proves acceptance).
3. Else → decrypt once, insert, record the stanza-id → `inserted`.

Display order is `sort_key` = server time (`<delay>` for offline/MAM copies, receive time for live), tie-broken by
`local_id`. It never depends on arrival order. The MAM cursor advances only after the page is committed.

**Do not rely on stanza-ids alone:** t02(b) measured two server copies of one logical message with different
stanza-ids. Only the origin-id identifies them as the same message.

| t09 | Cellular-like reconnect | PASS | both sides dropped, 8 s gap, new TCP connections, both resumed; 3 visible |

In every scenario: no logical message is visible twice, and **decrypt calls = inserted messages**.

## Findings that change the implementation

1. **One logical message may have several server ids.** docs/03 schema changed: `message.stanza_id` replaced by
   table `message_server_id(archive_jid, stanza_id, local_id)`. The single column could not represent t02(b).
2. **An ack request can overtake the message.** An `<r/>` sent right after `send()` can reach the server before the
   message leaves an async send queue, and the resulting `<a h>` does not cover it (observed with slixmpp). Rule
   for our transport: request acks only after the message has been written to the socket.
3. **After `<resumed/>`, request an ack.** Stanzas re-sent from the SM queue otherwise stay unacked until the next
   window, and the outbox shows them as pending.
4. `resend_on_timeout: if_offline` turns unacked live stanzas of a dead session into offline messages. Together
   with MAM catch-up this **guarantees duplicates** after a failed resume (t05), so dedup is mandatory, not defensive.
5. The UI's "sent" state may come from either the SM ack or a server copy (MAM/carbon) of our own message (t14).
